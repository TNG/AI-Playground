# One global Turn Queue; a turn holds its place until it is done

Agent Sessions used to be one at a time: leaving a session stopped its turn, and nothing stopped a Chat turn on another model from restarting the server under a running agent turn, while an Image Gen click during a turn was refused. There is now one Turn Queue for the whole app, kept by the orchestrator. Agent turns (every agent preset, local and cloud), local Chat and Home Agent turns, title summaries and Image/Edit/Video panel runs wait in it first come, first served; cloud Chat and cloud Home Agent turns and RAG embedding do not. One member holds the place for its whole turn, including the media it generates itself, and readiness (backend + model) runs when it takes the place, so a model swap only ever happens between turns. A member that waits on the user gives its place up and takes it back at the front of the queue before its next model call. Sessions are therefore concurrent, not parallel: any number can have a turn in flight, one calls the model.

## Considered Options

- **Parallel slots** (llama.cpp `--parallel`, or two servers loaded at once) — rejected: llama.cpp divides its context window between slots and the turns share one GPU's throughput, and two large models rarely fit in vRAM together. Turns on different models would still need a swap, which can only happen with no turn streaming.
- **Exclusive per model call instead of per turn** — rejected: a turn on model A interleaved with a turn on model B would swap the server between every step, each swap costing a full model load and the KV cache; an agent turn is dozens of steps.
- **An agent-only queue** — rejected: Chat, Home Agent, summaries and panel runs compete for the same server, so an agent-only queue leaves the original crash (a Chat turn restarting the server mid-turn) in place. The cost is that a Chat question can wait behind a long agent turn, shown as "Queued (Nth), waiting for …".
- **Exempting cloud agent turns** — rejected for one rule per kind of work: an agent turn's media tools still use the local GPU mid-turn, and "agent turns queue" is easier to predict than a rule that depends on the selected model. Cloud Chat and cloud Home Agent turns stay exempt because they are short, use no local GPU unless a tool asks, and are expected to answer at once.
- **Holding the place while waiting on the user** — rejected: a confirmation or download prompt in a session nobody is looking at would block every other session until the user came back. A paused turn yields; reclaiming at the front keeps it from being overtaken by work sent after it.
- **Persisting the queue across a restart** — rejected: the app would start heavy work by itself at launch. A turn that never ran is shown as "not run" with a resend action instead.
